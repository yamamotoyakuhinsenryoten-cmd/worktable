# 要件定義: Instagramトークンの自動更新と暗号化保存

- 作成日: 2026-11-23
- 更新日: 2026-11-24
- 対象: Worktable（`/api/post-instagram` が使うInstagramアクセストークン）
- ステータス: 確定

## 1. 背景・目的

Instagramの長期トークンは約60日で期限切れになり、切れるとWorktableの投稿機能が止まる。手動更新だと忘れるリスクがあるため、月1回の自動更新に切り替える。
あわせて、トークンをDBに暗号化して保存し、アプリ用のDBロールを権限を絞った形で分けることで、漏えい時の影響を小さくする。学習目的も含む。

## 2. 対象と非対象

- 対象：Instagramアクセストークンの更新・暗号化保存・DB読み込み、更新結果のメール通知、DBロール（worktable_app）の作成と権限付与
- 非対象：GitHub PAT（GitHub Appへの移行は別件としてやりたいことリストに登録済み）、mountain-book-dyeshop側の投稿処理（2026-11-24に対応不要と決定）、テストの設計（別件としてやりたいことリストに登録済み）

## 5. 制約

- refresh APIは、トークンの発行から24時間以上経過し、かつ期限切れ前の場合のみ使える。R-15 の30日条件により満たす
- Vercel Hobbyプランは、Cronを1日1回まで実行できる。R-03 の毎日起動はこの範囲内
- Vercel Cronの時刻はUTCで指定する。日本時間に直すと、毎日 03:00 JST は 18:00 UTC
- Vercel Cronは指定時刻ちょうどに動くとは限らず、前後にずれることがある。毎日起動の設計はこのずれを前提にする
- 失敗が続く間は、毎日メールが届く（期限切れに気づけるようにするため）
- 期限切れなどで更新が続けて失敗し、トークンが使えなくなった場合は、Instagramで新しいトークンを発行し、初回投入スクリプトで再投入する
- メール送信に失敗しても、更新処理の結果（DBの更新の有無）は変えない
- 既存の Instagram Graph API のバージョン（v24.0）は変えない
- トークンの値（平文・暗号文・鍵）はログに出力しない。エラーメッセージにも含めない
- パスワード・鍵・GmailのアプリパスワードをマイグレーションファイルやGitに含めない
- 暗号化に使う鍵は32バイトのランダム値とし、環境変数に保存する。紛失した場合は再発行で対応する（再発行すると、既存の暗号文は復号できなくなるため、トークンの再投入が必要）

## 付録A: 学習ノート用

- 目的・経緯：Instagramトークンが60日で切れるため、手動更新の忘れを防ぎたい。同時に、暗号化とDBロールの分離を学ぶ題材にする
- 検討した案：
  - A案：手動で60日ごとに再発行する。単純だが、忘れると投稿が止まる
  - B案：Cronで自動更新し、暗号化してDBに保存する。自動化できるが、トークンを扱う仕組みが増える
  - 採用：B案
- 採用理由：自動化で止まるリスクを減らせる。暗号化とDBロールの分離で、漏えい時の影響も小さくできる
- 学んだこと（暗号化方式）：
  - 共通鍵暗号：同じ鍵で暗号化と復号をする。自分のデータを自分で守る用途に向く
    - AES-256-GCM（採用）：認証付き。暗号文の改ざんを検知できる。PCやサーバーで広く使われる
    - ChaCha20-Poly1305：認証付き。ソフトウェアだけで速く動くため、スマホなどで使われる
    - AES-CBC・AES-CTR：認証なし。改ざんを検知するには別の仕組みが必要。古い実装で見かける
  - 公開鍵暗号：公開鍵で暗号化し、秘密鍵で復号する。鍵を相手に渡せるため、通信の鍵交換（HTTPSなど）や署名に使う
    - RSA：鍵交換と署名。古くから使われる
    - X25519：鍵交換。HTTPSの通信で使われる
    - Ed25519・ECDSA：署名。改ざんされていないことや、本人が作ったことを確認する
  - ハッシュ：一方向の変換。元に戻せない
    - SHA-256：データの整合性の確認
    - bcrypt・Argon2・scrypt：パスワードの保存。わざと遅くして総当たりを防ぐ
  - 今回の判断：トークンは更新時に取り出して使う必要があるため、ハッシュではなく暗号化を選んだ。自分のアプリの中で鍵を共有すれば足りるため、公開鍵暗号は使わない
- 学んだこと（用語）：
  - PAT（Personal Access Token）：GitHubの個人用の鍵。権限が広く、漏れると影響が大きい。GitHub Appは、権限を絞ってアプリ単位で管理できる仕組み（別件で検討）
  - マイグレーション：DBの構造（テーブルなど）の変更を、番号付きのSQLファイルで順番に管理する仕組み。今回は `006_create_app_secrets.sql` を作る。構造変更はオーナー権限で実行する
  - Vercel Cron：決まった時刻にVercelのURLを呼び出す仕組み。Hobbyプランは1日1回まで。時刻はUTCで、ずれることがある
  - Bearer認証：`Authorization: Bearer <トークン>` の形で合言葉を送る方式。`CRON_SECRET` と一致するかで呼び出し元を確認する
  - DBロール：DBの中のユーザー。権限を付けたり外したりでき、アプリには必要最小限の権限だけを持たせる。Neonのコンソールへのログインとは別物
  - IV（初期化ベクトル）：暗号化のたびにランダムに作る値。同じ平文でも毎回違う暗号文になるように使う。暗号文と一緒に保存する
  - 認証タグ：GCMが作る改ざん検知用の値。復号時に一致しなければエラーになる
  - UPSERT：既存の行があれば更新し、なければ挿入する操作
  - アプリパスワード（Gmail）：通常のパスワードではなく、メールの送信などアプリ用に発行する専用のパスワード。Googleの2段階認証を有効にしていると使える
  - 環境変数のSensitive：Vercelで一度保存すると値が画面に表示されなくなる設定
- 時刻の注意：Vercel CronはUTCで動く。日本時間の 03:00 は UTC の前日 18:00。設定時に取り違えやすい
- 残課題：GitHub PATのGitHub App化（別件）、テストの設計（別件。どんなテストが必要かを自分で検討する）
